# 데이터 정책 및 시드 정의서

> 목적: Phase 1 DB 작업(`S-1-1`~`S-1-9`)을 시작하기 전에 "임의로 정해질 수 있는 것"을 미리 확정. 이 문서는 마이그레이션/시드 작성 시 그대로 옮겨 쓰는 원본(Source of Truth)입니다.

---

## 1. 시드 데이터 (시스템 기본값)

### 1-1. 기본 항목분류(CATEGORY) — `S-1-1`에서 시드

실제 사용 데이터(첨부 이미지) 기준으로 확정. `is_system_default = true`, `user_id = null`.

| 카테고리명 | 부모 | 아이콘(예시) |
| ---------- | ---- | ------------ |
| 식료품     | -    | 🛒           |
| 의류       | -    | 👕           |
| 주거       | -    | 🏠           |
| 보험       | -    | 🛡️           |
| 구독료     | -    | 📱           |
| 관리비     | -    | 🏢           |
| 회비       | -    | 🤝           |
| 용돈       | -    | 💸           |
| 교통       | -    | 🚗           |
| 의료/건강  | -    | 🏥           |
| 기타       | -    | 📦           |

> 사용자가 직접 추가/수정 가능(F-1-1-2). 위 목록은 "처음 가입 시 보이는 기본값"일 뿐 고정값이 아님. 마지막 3개(교통/의료/용돈 외 기타)는 일반적으로 자주 쓰이는 항목이라 추가했으니, PM이 보기에 불필요하면 시드에서 빼도 됨.

### 1-2. 기본 지출분류(PAYMENT_METHOD) — `S-1-2`에서 트리거로 자동 생성

회원가입 시 DB 트리거(`auth.users` INSERT)로 아래 1종을 해당 `user_id`로 자동 생성. 사용자가 `display_name` 수정 가능, `is_active` 비활성화만 앱 레벨에서 제한.

| type | subtype    | display_name | 비고                             |
| ---- | ---------- | ------------ | -------------------------------- |
| CASH | CASH_SPEND | 지갑(현금)   | 가입 시 자동 생성, 비활성화 불가 |

카드 및 은행 계좌(통장)는 사용자가 F-1-1-1에서 직접 등록.

> **"자동이체"라는 단어는 UI에 노출하지 않는다.**
> 통장에서 돈이 주기적으로 빠져나가는 행위(자동이체)의 본질은 "어떤 통장(은행)에서 나갔는가"이다.
> 따라서 지출 입력 시 사용자는 "현금 → 신한은행"을 선택하고, 카테고리에서 "고정비 → 월세" 또는 "저축 → 적금"을 선택하게 유도한다.
> DB에서 은행 계좌는 `type=CASH`, `subtype=AUTO_TRANSFER`로 저장하지만, 이 내부 코드는 화면에 노출하지 않는다.
> (출처: 기획 결정 2026-06-27 — 사용자 가이드/앱 기획서 작성 시 이 코멘트를 기준으로 삼을 것)

### 1-4. 동의어 사전(SYNONYM_DICTIONARY) 초기값 — `S-3-1` 계열, Phase 3에서 시드

## 2. 비즈니스 규칙 / 예외 처리 정책

이 항목들은 코드를 짜기 전에 "이렇게 하기로 정함"을 명문화한 것입니다. 구현 중 애매하면 여기로 돌아와서 확인.

| 항목                                           | 정책                                                                                                                                                                                                                                                                      |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 금액(amount) 음수 허용?                        | **허용하지 않음(0보다 커야 함)**. 환불/취소는 별도 트랜잭션으로 기록하지 않고, 1단계에서는 해당 트랜잭션을 수정/삭제하는 것으로 처리(환불 전용 기능은 범위 밖, 필요시 추후 별도 설계).                                                                                    |
| 상세항목 합계 ≠ 총액일 때                      | `TRANSACTION.amount`는 상세항목 합계로 **자동 계산되며 직접 수정 불가**. 영수증 부가세/할인 등으로 실제 결제액이 다르면 `adjustment_amount`에 차액을 입력 (`amount = SUM(detail.amount) + adjustment_amount`로 최종 표시).                                                |
| CATEGORY 삭제 시, 연결된 TRANSACTION이 있으면? | **삭제 금지(soft delete만 허용)** — `is_active=false`로 비활성화만 가능. 기존 트랜잭션의 분류는 유지되고, 새 입력 시 선택 목록에서만 숨김.                                                                                                                                |
| VENDOR 삭제 시                                 | 위와 동일하게 **soft delete**(비활성화). 과거 데이터 보존 우선.                                                                                                                                                                                                           |
| ITEM(상세항목) 삭제 시                         | **삭제 기능 자체를 제공하지 않음** — 잘못 만든 항목은 "병합(merge)"으로 다른 항목에 합치는 것만 허용(F-1-1-8). 완전 삭제는 집계 데이터 정합성을 깨뜨릴 수 있어 막음.                                                                                                      |
| PAYMENT_METHOD(카드/은행) 삭제 시              | **soft delete**(`is_active=false`). 지갑(현금) 1종(`is_system_default=true`)은 비활성화도 불가 — 앱 레벨에서 제한.                                                                                                                                                        |
| 동일 지출처/품목 이름 중복 등록                | 같은 사용자 내에서 **이름 완전 일치 시 자동완성에서 우선 노출**하지만, 중복 생성 자체를 DB 레벨에서 막지는 않음(유니크 제약 없음) — 화면 자동완성으로 유도하는 정책. 단, `external_id + source_app`(서브앱 연동 트랜잭션)은 DB 유니크 제약으로 멱등성 강제(아키텍처 4장). |
| 미래 날짜 지출 입력 허용?                      | 허용(예: 자동이체 예약일 미리 기록 등 실사용 시나리오 고려). 단, 대시보드 "이번달 지출" 집계는 `occurred_at` 기준으로만 계산.                                                                                                                                             |
| 수량/단위 구조화 실패("1+1")                   | 금액 집계(Top10 등)에는 포함, 단가 통계(`item_unit_stats`)에서는 제외 — 아키텍처 5장에서 이미 확정한 내용 재확인.                                                                                                                                                         |
| 예산(BUDGET) 초과 시 동작                      | 입력을 막지 않음(경고만 표시) — 가계부는 기록이 우선이지 통제 도구가 아님.                                                                                                                                                                                                |

## 3. RLS 정책 표 (테이블별, `S-1-9`에서 그대로 구현)

모든 정책의 기본 원칙: **`user_id = auth.uid()`인 행만 조회/수정 가능.** 예외만 아래 표에 표기.

| 테이블               | SELECT                                   | INSERT                                                     | UPDATE                                                                                    | DELETE                                                                                                 |
| -------------------- | ---------------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `CATEGORY`           | 본인 것 + `user_id IS NULL`(시스템 기본) | 본인 것만 (user_id = auth.uid()로 강제)                    | 본인 것만, 시스템 기본은 불가                                                             | 정책상 막음(2장 soft delete 정책) — UPDATE(`is_active=false`)로 대체, DELETE 정책 자체를 생성하지 않음 |
| `PAYMENT_METHOD`     | 본인 것만                                | 본인 것만                                                  | 본인 것만, 지갑(현금)(`is_system_default=true`, `is_active` 불변)은 앱 레벨에서 추가 검증 | 없음 (soft delete만)                                                                                   |
| `VENDOR`             | 본인 것만                                | 본인 것만                                                  | 본인 것만                                                                                 | 없음 (soft delete만)                                                                                   |
| `ITEM`               | 본인 것만                                | 본인 것만                                                  | 본인 것만 (merge 포함)                                                                    | **정책 없음 — 삭제 기능 자체 미제공**                                                                  |
| `UNIT`               | 본인 것 + `user_id IS NULL`(시스템 기본) | 본인 것만                                                  | 본인 것만                                                                                 | 없음                                                                                                   |
| `TRANSACTION`        | 본인 것만                                | 본인 것만, `amount > 0` 체크는 CHECK 제약으로 DB 레벨 강제 | 본인 것만                                                                                 | 본인 것만 허용(직접 삭제는 허용 — 비활성화 정책 없음, 트랜잭션 자체는 진짜 삭제 가능)                  |
| `TRANSACTION_DETAIL` | 부모 TRANSACTION이 본인 것인 경우만      | 부모 TRANSACTION이 본인 것인 경우만                        | 부모 TRANSACTION이 본인 것인 경우만                                                       | 부모 TRANSACTION이 본인 것인 경우만                                                                    |
| `BUDGET`             | 본인 것만                                | 본인 것만                                                  | 본인 것만                                                                                 | 본인 것만                                                                                              |
| `ACCOUNT_LINK`       | 본인 것만                                | 본인 것만                                                  | 본인 것만                                                                                 | 본인 것만                                                                                              |
| `SUB_APP`            | 전체 공개 읽기(목록 노출용)              | **운영자만**(앱에서 INSERT UI 자체를 제공하지 않음)        | 운영자만                                                                                  | 운영자만                                                                                               |
| `SUB_APP_ITEM_MAP`   | 본인 것만                                | 본인 것만                                                  | 본인 것만                                                                                 | 본인 것만                                                                                              |
| `SYNONYM_DICTIONARY` | 전체 공개 읽기                           | **운영자만**                                               | 운영자만                                                                                  | 운영자만                                                                                               |

> "운영자만"은 1단계에서는 **별도 운영자 role 없이 Service Role Key로 직접 SQL 실행**하는 방식으로 충분(어드민 화면은 Phase 3, `F-3-1-5`에서 별도 구현). 운영자 화면이 생기기 전까지는 RLS에서 그냥 "일반 사용자 INSERT/UPDATE/DELETE 정책을 만들지 않음"으로 처리(=클라이언트로는 불가능, Service Role Key로만 가능).

## 4. 이 문서의 사용 시점

- `S-1-1`(CATEGORY), `S-1-2`(PAYMENT_METHOD), `S-1-5`(UNIT) 마이그레이션/시드 작성 시 → **1장**을 그대로 `seed.sql`에 반영
- `S-1-9`(RLS 정책 작성) 시 → **3장** 표를 그대로 SQL 정책으로 변환
- 지출 입력/마스터 데이터 화면(F-1-1-x) 구현 중 "이 경우 어떻게 하지?" 싶을 때 → **2장** 확인
- 정책이 실제로 안 맞는다고 판단되면, 코드만 바꾸지 말고 **이 문서를 먼저 수정**한 뒤 구현 변경 (CLAUDE.md의 "설계서 변경 시 보고" 규칙과 동일)
