### 사용자 가이드 참고 — 품목 병합 동작 설명 (2026-07-04 PM 문의 대응, 같은 날 동작 수정 반영)

> 이 절은 나중에 사용자 가이드를 쓸 때 그대로 옮겨 쓸 수 있도록 사용자 관점 언어로 정리한 것 — PM 문의 "병합했는데 지출 보기엔 여전히 옛 이름으로 보인다. 병합은 언제 쓰이는 거냐"에서 시작해, "병합한 의도는 앞으로도 같은 이름으로 입력하면 계속 하나로 잡히길 원하는 것"이라는 PM 확인에 따라 동작을 수정함.

- **병합은 "표시 문구"를 바꾸지 않습니다.** 지출을 입력할 때 실제로 타이핑한 텍스트(예: "깐 양파")는 영수증처럼 그대로 남습니다 — 지출 보기/수정 화면에 계속 그 문구로 보이는 게 정상입니다.
- **병합이 하는 일은 "이 지출을 통계에서 어떤 품목으로 계산할지"를 다시 연결하는 것입니다.** 병합하는 순간 과거 지출들은 즉시 새 품목("양파") 기준으로 재연결됩니다.
- **병합하는 목적은 결국 품목별 통계(Top10 등)를 정확히 보기 위함입니다.** "깐 양파"와 "양파"를 따로 세면 통계가 갈라지니, 병합해서 하나로 합쳐 보려는 것 — 즉 병합은 "지금 당장의 화면 표시 변경"이 아니라 "나중에 통계를 정확히 합산하기 위한 사전 작업"입니다.
- **병합 이후 새 지출을 입력할 때(2026-07-04 수정 후)**: "깐 양파"라고 타이핑하면 자동완성에 "양파"가 뜨는데, **그 제안을 클릭해서 선택하지 않고 그냥 타이핑만 하고 넘어가도** 서버에서 이름/별칭 일치 + 병합 체인을 따라가 자동으로 "양파"로 연결됩니다. 즉 병합해두면 그 이후로는 "깐 양파"든 "양파"든 어떻게 입력해도 항상 하나의 품목으로 잡힙니다.
  - **수정 전 알려진 문제**: 원래는 자동완성 제안을 직접 클릭해야만 병합된 품목으로 연결되고, 그냥 타이핑만 하면 이름이 정확히 일치하는 옛 품목("깐 양파", 병합되어 화면엔 안 보이지만 데이터는 남아있음)을 그대로 재사용해 "한 다리 건너" 연결되는 문제가 있었음 — `apps/main/web/app/(app)/expenses/actions.ts`의 `resolveItemId`가 이름 완전일치만 검사하고 별칭·병합 체인을 확인하지 않았기 때문. 사용자 실제 데이터로 재현 후(`transaction_detail`/`item` 조인 쿼리) 수정 완료 — 회원가입→상세입력 2건("양파"/"깐 양파" 각각 신규 생성)→병합→병합 후 "깐 양파" 재입력(자동완성 미선택) 전체 흐름을 재현해, 새 항목이 옛 "깐 양파" 품목이 아니라 "양파"에 직접 연결되는 것을 DB 조회로 확인.
- (개발 메모) 품목별 통계 화면(F-3-1-3, Top10) 자체는 아직 미착수 — 다만 위 수정으로 병합 시점 이후의 신규 지출은 항상 최종 대표 품목 id로 즉시 연결되므로, 이 화면이 만들어지면 단순히 `item_id` 기준으로 집계해도 정확함(기존에 유일하게 남아있던 위험은 병합 전에 이미 저장된 과거 데이터인데, 그건 병합 시점에 이미 일괄 재배정됨). `lib/item-merge.ts`의 `resolveCanonicalItemId`/`groupByCanonicalItem`은 그래도 방어적으로 유지 — 혹시 모를 재배정 누락(멀티 스테이트먼트 트랜잭션 미지원 등)에 대비.
- (개발 메모) 이 수정은 서버 액션(`resolveItemId`)의 DB 조회 로직 변경이라 스키마/UI 자동화 테스트로 커버하기 애매해 자동 회귀 테스트는 아직 없음 — 위 시나리오를 Playwright로 수동 재현 + DB 직접 조회로 검증. 필요하면 추후 별도 E2E/통합 테스트로 승격 검토.

## T-5-4 — 성능 점검 (대시보드 응답속도, MV/캐시 효과 확인)

> 2026-07-08 구현. 이 TASK는 기능/보안 회귀가 아니라 **속도 측정**이 목적이라, 다른 T-5-x와 접근 방식이 다르다 — ① MV(S-3-1~3)/캐시(S-3-5~6)의 실제 효과는 대량 데이터를 시딩해 DB 레벨(`EXPLAIN ANALYZE`)과 Redis 직접 호출로 한 번 측정해 수치로 기록(투자적 벤치마크, CI에 상시 자동화하기엔 대량 시딩·네트워크 의존적 절대 수치라 부적합), ② 회귀 스위트에는 "터무니없이 느려지지 않았는가"를 매번 감시하는 가벼운 예산(budget) 가드(`e2e/performance.spec.ts`)만 커밋.
>
> **측정 방법**: `npx supabase db query --local`로 로컬 DB에 SQL을 직접 실행해 한 테스트 사용자에게 트랜잭션 1,500건 + 상세항목 1,400건(품목 150종, 지출처 30곳에 고르게 분산 — 처음엔 서브쿼리가 uncorrelated라 Postgres가 딱 1회만 평가하고 재사용해버려 전부 같은 값으로 쏠리는 걸 발견, `t.id IS NOT NULL` 같은 무해한 상관 조건을 넣어 행마다 재평가되도록 수정)를 시딩 → MV(`item_stats`/`tx_stats`)가 트리거로 자동 갱신된 것 확인(각각 736행/1,052행) → 벤치마크 후 즉시 삭제(FK 순서상 `transaction`을 배치로 나눠 삭제 → cascade로 `transaction_detail` 자동 정리 → `item`/`vendor`/`auth.users` 순, 대량 삭제 한 번에 시도하면 락 관련 `out of shared memory` 발생해 200건씩 배치 처리).
>
> **① MV 효과 (DB 레벨, `EXPLAIN ANALYZE`)** — 같은 결과를 "원본 테이블 직접 JOIN+GROUP BY"와 "MV 조회"로 각각 실행:
>
> | 쿼리                                     | 방식                                                    | Execution Time | 실행 계획            | Buffer hits |
> | ---------------------------------------- | ------------------------------------------------------- | -------------- | -------------------- | ----------- |
> | 상세항목 Top10(2026-04, item_stats 대응) | 원본(`transaction_detail` JOIN `transaction`, GROUP BY) | **1.011ms**    | Seq Scan + Hash Join | 140         |
> | 상세항목 Top10(2026-04)                  | MV(`item_stats`)                                        | **0.162ms**    | Bitmap Index Scan    | 13          |
> | 지출처 Top N(2026-04, tx_stats 대응)     | 원본(`transaction` 직접 GROUP BY)                       | **0.664ms**    | Seq Scan             | 96          |
> | 지출처 Top N(2026-04)                    | MV(`tx_stats`)                                          | **0.309ms**    | Bitmap Index Scan    | 21          |
>
> 현재 데이터량(사용자당 트랜잭션 1,500건 수준)에서도 MV가 **약 2~6배 빠르고 buffer hit이 7~10배 적다** — 원본 쿼리는 데이터가 늘수록 Seq Scan 비용이 선형으로 증가하지만 MV는 인덱스 조회라 사실상 일정하게 유지되므로, 데이터가 몇 년치 쌓일수록 이 격차는 더 벌어질 것으로 예상됨(설계서 5장의 "raw 테이블 join/group by는 품목 수가 늘어날수록 느려지므로 MV 필수" 전제와 일치).
>
> **② 캐시 효과 (Redis, S-3-6 item_top10) — ⚠️ 예상과 다른 결과 발견**: `get_item_stats` RPC(로컬 Postgres, PostgREST 경유) 직접 호출은 **2~10ms**, 반면 Upstash Redis(`item_top10` 캐시 키) GET 직접 호출은 **200~300ms**로 오히려 **Redis 캐시 쪽이 20~100배 더 느렸다.** 원인은 이 개발 환경 특성 — 로컬 Postgres(같은 머신, `127.0.0.1`)는 사실상 지연이 없는데 Upstash는 인터넷 건너 클라우드 서비스라 매 호출마다 실제 네트워크 왕복(RTT)이 들어간다. 그 결과 대시보드 전체 로드 시간으로 봐도 캐시 미스(869ms) 대비 캐시 히트(765~782ms)가 **약 10~12%만 빨랐다**(RPC는 여러 통계 쿼리와 병렬 실행되는 쿼리 중 하나라 병목이 아닌 경우가 많아 전체 페이지 체감 효과는 격차 대비 작게 나타남).
>
> **PM 참고**: 로컬 개발 환경에서는 캐시가 "속도"를 위해서라기보다 **오히려 손해**에 가깝게 측정됐다 — 하지만 이건 로컬 Postgres가 유별나게 빠른 상황(같은 머신) 때문이지 캐시 설계가 잘못된 게 아니다. 실제 이 캐시의 값어치는 ①프로덕션(Supabase Cloud DB도 네트워크 건너편이라 Redis와 RTT가 비슷해짐 — RPC 대비 손해가 사라짐) ②트래픽이 늘었을 때 반복되는 동일 쿼리로 인한 DB 부하/컴퓨팅 비용 절감(지연시간이 아니라 "얼마나 자주 DB를 두드리는가"의 문제) 두 가지에서 나온다. 지금 로컬에서 "느려 보인다"고 캐시를 걷어내는 건 잘못된 결론이라, 이번엔 그대로 유지.
>
> **③ 대시보드 종단 응답 시간**: 신규(빈) 계정 기준 첫 로드 736~1,672ms, 재방문 731~1,400ms(샌드박스 환경 부하에 따라 변동 — 로컬 단독 실행 시 더 빠름) — `performance.spec.ts`의 5초 예산 안에 항상 여유 있게 들어옴.

## T-2-1 — 관리비 명세서 업로드 플로우 단위테스트 (최초/재업로드-동일형식/형식변경, F-2-1-1~3 커버)

> 2026-07-18 구현(2차 개발). **범위 확정(PM 확인)**: WBS는 "최초/재업로드-동일형식/형식변경" 3케이스를 요구하지만, S-2-9에서 만든 형식변경 판정 함수(`calculateFormatMatchRate`/`isSameFormat`)는 백로그 B-13 결정에 따라 실제 업로드 플로우(`checkPeriodConflictAction`/`saveUtilityBillAction`)에 아직 연동되어 있지 않다(재업로드는 형식이 같든 다르든 항상 `confirm_needed`로 동일 처리) — 그래서 "형식변경"은 판정 함수가 아니라, `saveUtilityBillAction`이 이미 실제로 하는 **라벨 기준 `UTILITY_BILL_ITEM` upsert**(기존 라벨이면 재사용, 처음 보는 라벨이면 신규 생성)로 구현해 테스트했다. 이 레포에서 `createSupabaseServerClient()`를 통째로 모킹해 server action을 단위테스트한 첫 사례(기존엔 `stats-cache.ts`처럼 supabase를 파라미터로 받는 함수만 테스트 가능했음, PM 확인 후 채택) — `from(table)` 체이닝 빌더가 테이블별로 큐잉된 응답을 순서대로 반환하는 방식.
>
> **부수 발견**: `actions.ts`가 값 import로 쓰는 `@/lib/utility-bill-schemas`를 처음 직접 로드하며 vitest가 `@/` 별칭을 해석 못 해 실패 확인 — 기존 테스트는 전부 `@/...` import가 `import type`이라 트랜스파일 시 제거돼 드러나지 않았던 갭. `vitest.config.ts`에 `resolve.alias`로 tsconfig의 `@/*`와 동일하게 매핑해 해결.
