# 지출 관리 가계부 — WBS (Work Breakdown Structure) — 2차 개발

> 기준 문서: `docs/2차/관리비명세서_데이터구조설계.md`, `docs/2차/관리비명세서_화면설계.md`, `docs/기능명세서_IA.md`(F-1-2-x), `가계부_아키텍처_설계.md`, `데이터정책_및_시드정의서.md`
> 작업 코드 체계: **`S-`** = 시스템 구현, **`F-`** = 앱 기능, **`T-`** = 테스트, **`PM-`** = Claude Code 세션이 아닌 PM 단독 수행 작업. 2단계(Phase 2)에서 서브앱 전제로 부여됐던 `S-2-x`/`F-2-x`/`T-2-x` 번호대를 관리비 명세서(메인앱 내장) TASK로 재사용합니다 — 원 서브앱 TASK 목록은 `docs/2차/인수인계.md`에 원문 보존.
> 개발 방식: **PM 1인 + Claude Code 바이브 코딩** — 1차와 동일하게 Claude Code 터미널 세션 단위로 작업하며, TASK 하나가 끝나면 PM이 결과를 확인한 뒤 다음 TASK로 진행합니다(CLAUDE.md "작업 진행 방식" 원칙 그대로 적용).

---

## 0. 일정 추정 전제 (Claude 세션 관리 기준, 1차 WBS와 동일 가정 유지)

1차 WBS 작성 시점의 가정을 그대로 이어받습니다. 실제 소진 속도는 1차 진행 중 관찰한 값으로 보정하는 것을 권장합니다.

| 가정 항목                | 내용                                                                                                                                               |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 작업 단위                | 1세션 = Claude 사용량 롤링 윈도우 1회(Claude Code 터미널 세션 기준)                                                                                |
| 1세션당 처리량           | 소규모 TASK 1~2개 — TASK를 세션 안에 끝낼 수 있는 크기로 분해하는 원칙은 2차에도 동일 적용                                                         |
| 1일 가용 세션            | 1일 1~2세션 수준으로 가정(모델/작업 복잡도에 따라 유동적)                                                                                          |
| TASK 크기 기준           | 모든 TASK는 **"한 세션 안에 끝낼 수 있는 단위"**(약 0.2~0.8세션)로 분해. 그보다 크면 하위 TASK로 추가 분할                                         |
| PM 전용 작업(`PM-` 코드) | Claude Code 세션을 소비하지 않는, PM이 레포 루트/외부 서비스에서 직접 수행하는 작업(Git 태그, OCR 벤더 실사용 결제/가입 등). 세션 수 합계에서 제외 |

**일정 환산**: `예상 세션 수 ÷ 1일 가용 세션(1~1.5) = 예상 소요일` (주말 제외, 매일 작업 가정)

> ⚠️ 1차와 마찬가지로 TASK 하나를 끝내면 자체적으로 다음 TASK로 넘어가지 않고 멈춰서 PM에게 결과를 보여줍니다. 한 세션에 여러 TASK를 욕심내어 처리하지 않습니다.

## 7. 작업 순서 권장 원칙

1. **선행작업(2장) 중 `PM-0-1`(Git 태그)은 착수 전 반드시 먼저 처리**. `S-1-13`은 순서상 자유롭게 미뤄도 되며 2차 마지막에 배치합니다.
2. **DB(3장) → OCR(4장) → 화면(5장) 순서 고정** — 1차와 동일한 원칙(DB 먼저, 화면 나중).
3. **4장(OCR 연동)이 최대 리스크 구간**입니다. `PM-4-1`(벤더 선정)이 지연되면 이후 5장 전체가 밀리므로, 가능한 한 빨리 착수하는 것을 권장합니다.
4. **5-1(업로드) → 5-2(항목 선정) → 5-3(통계) → 5-4(기존 화면 연계) 순서 고정** — 화면설계 문서의 플로우 순서와 동일합니다.
5. **테스트(T-코드)는 각 기능 블록이 끝날 때마다 바로 진행**합니다.
6. 이 Phase가 끝나면 CLAUDE.md 원칙에 따라 `develop` → `main` 릴리즈 PR을 PM에게 먼저 안내합니다.
