# 관리비 명세서 — 데이터 구조 설계

> 작성일: 2026-07-11
> 목적: 2차 개발 "관리비 명세서" 기능의 데이터 구조를 확정합니다. `docs/2차/인수인계.md` 4장 원칙("관리비 명세서 설계 — 데이터 구조 → 화면설계 → 기능명세 — 가 WBS 작성보다 선행")에 따라 이 문서를 가장 먼저 작성합니다. 이 문서 확정 후 화면설계 문서로 이어갑니다.

## 0. 범위 결정 배경

- 관리비는 별도 서브앱이 아니라 **메인 가계부 앱의 내장 기능**으로 개발합니다(2026-07-11 PM 결정). 콘텐츠 관점에서 관리비 기능은 가계부의 지출분류·지출처 체계에 종속적이라 독립 실행 시나리오의 가치가 낮고, Webhook/계정연결 인프라(인수인계.md 2장 4-1~4-3 원안)를 걷어낼 수 있어 개발 범위가 크게 줄어듭니다.
- 인수인계.md 2장의 서브앱 전제 TASK 목록(S-2-1~S-2-11 등)은 이 결정으로 더 이상 유효하지 않습니다. WBS 작성 시 F-1-x 스타일의 신규 기능 코드로 재정의합니다.
- **1인 1세대**를 기준으로 MVP 범위를 잡습니다. 여러 세대/건물을 동시에 관리하는 시나리오는 범위 밖이며, 필요 시 `docs/백로그.md`에 기록합니다.

## 1. 전체 흐름 요약

### 1-1. 진입 경로 2가지

- **수동 입력**: 기존 지출 입력 화면(F-1-1-4)에서 카테고리를 "관리비/공과금"으로 선택해 금액을 직접 입력합니다. 화면 자체는 변경하지 않습니다.
- **명세서 업로드**: 신규 메뉴 "관리비 명세서" 하위의 "명세서 업로드" 화면에서 사진/PDF를 업로드하면 OCR로 추출 후 등록합니다.

### 1-2. 메뉴 구조

"관리비 명세서"(상위 메뉴) 아래 "명세서 업로드" | "명세서 통계"(하위 메뉴) 두 화면으로 분리합니다. 각 화면에는 서로에게 이동하는 버튼을 둡니다(업로드 화면 → "통계 보기", 통계 화면 → "새로 업로드").

### 1-3. 업로드 처리 분기

화면을 나누지 않고, 하나의 업로드 플로우 안에서 서버 판별 로직으로 아래 3가지를 분기합니다.

1. **최초 업로드**: 사용자의 지정 항목(`UTILITY_BILL_ITEM`)이 하나도 없음 → 항목 선정 페이지로 진입
2. **재업로드(형식 동일)**: 추출된 라벨이 기존 지정 항목과 대부분 일치 → 곧바로 확인 화면
3. **형식 변경 감지**: 추출된 라벨이 기존 지정 항목과 임계치 이상 불일치 → 항목 선정 페이지로 재진입(신규 항목 추가/기존 항목 비활성화)

> 형식변경 판별 임계치 값은 이 문서와 별개로, 통계 화면 콘텐츠 설계 시 함께 확정합니다(§7 참고).

## 2. 데이터 모델

### 2-1. 개념 요약

- 관리비 지출은 **총액만** 메인 `TRANSACTION`에 등록합니다(`has_detail=false`, 상세품목 미사용). 명세서의 개별 항목(일반관리비, 전기료 등)은 지출 데이터가 아니라 **통계 전용 데이터**로 별도 저장합니다.
- 항목 마스터(`UTILITY_BILL_ITEM`)는 사용자별로 완전히 독립적입니다. 시스템 공통 시드가 없고, 사용자가 최초 업로드 시 확인한 항목만 생성됩니다. 같은 사용자 안에서도 시간에 따라(양식 변경) 항목 구성이 바뀔 수 있어 `is_active`로 시점별 변화를 대응합니다.
- 초기에는 "개인공과(사용량표)"와 "공동공과(영수증표)"로 항목을 이원화해 각각 합계를 내려 했으나, 샘플 검증 결과 온수(사용량표)=급탕요금(영수증표)처럼 같은 항목이 두 표에 중복 노출되어 이중계산 위험이 확인되어 **폐기**했습니다. 대신 **영수증표 기준 단일 총액**으로 통일하고, 사용량표는 사용량 수치(`usage_value`, 계량기 원본값 포함)만 제공하는 보조 데이터로 취급합니다.

### 2-2. 관계 요약

```
TRANSACTION 1 --- 1 UTILITY_BILL_RECORD 1 --- N UTILITY_BILL_ITEM_VALUE N --- 1 UTILITY_BILL_ITEM
                                                                                (user_id 소유, 독립 마스터)
```

### 2-3. 테이블 정의

**`UTILITY_BILL_ITEM`** (사용자별 지정 항목 마스터)

| 컬럼          | 타입             | 설명                                                                                               |
| ------------- | ---------------- | -------------------------------------------------------------------------------------------------- |
| id            | uuid PK          |                                                                                                    |
| user_id       | uuid FK          |                                                                                                    |
| name          | string           | 표시명(전기료, 일반관리비 등)                                                                      |
| has_usage     | boolean          | 사용량 수치를 함께 저장하는 항목인지(전기료/수도료/급탕요금 등)                                    |
| usage_unit    | string, nullable | kWh, ㎥ 등 — `has_usage=true`인 경우만                                                             |
| source_labels | jsonb            | OCR 원문 라벨 매칭용 별칭 배열. 예: `["급탕요금", "온수"]`처럼 서로 다른 표기를 같은 항목으로 매칭 |
| is_active     | boolean          | soft delete(양식 변경 대응, `ITEM`/`CATEGORY`와 동일 원칙)                                         |
| created_at    | timestamp        |                                                                                                    |

**`UTILITY_BILL_RECORD`** (사용자의 월별 관리비 등록 1건)

| 컬럼                    | 타입                    | 설명                                                           |
| ----------------------- | ----------------------- | -------------------------------------------------------------- |
| id                      | uuid PK                 |                                                                |
| user_id                 | uuid FK                 |                                                                |
| period                  | string (YYYY-MM)        | **`UNIQUE(user_id, period)`** — 한 사용자당 한 달에 1건만 존재 |
| transaction_id          | uuid FK                 | `TRANSACTION`과 1:1                                            |
| source                  | enum('MANUAL','UPLOAD') | 수동입력/업로드 구분 — 재업로드 충돌 판정(§3-2)에 사용         |
| file_path               | string, nullable        | Storage 경로(`source='UPLOAD'`인 경우만)                       |
| created_at / updated_at | timestamp               |                                                                |

**`UTILITY_BILL_ITEM_VALUE`** (월별 항목 값)

| 컬럼           | 타입                          | 설명                                      |
| -------------- | ----------------------------- | ----------------------------------------- |
| id             | uuid PK                       |                                           |
| record_id      | uuid FK → UTILITY_BILL_RECORD |                                           |
| item_id        | uuid FK → UTILITY_BILL_ITEM   | **`UNIQUE(record_id, item_id)`**          |
| amount         | decimal                       | 항목 금액(영수증표 기준)                  |
| usage_value    | decimal, nullable             | 사용량 — `has_usage=true`인 경우만        |
| meter_previous | decimal, nullable             | 전월 계량기 원본 수치(정합성 검증/감사용) |
| meter_current  | decimal, nullable             | 당월 계량기 원본 수치                     |
| created_at     | timestamp                     |                                           |

### 2-4. TRANSACTION 연계 규칙

- `category_id`: 기존 "관리비/공과금" 카테고리(이미 존재, 2026-07-08 개명)를 그대로 사용합니다. 신규 카테고리를 만들지 않습니다.
- `vendor_id`: **"관리사무소"로 고정**(권장). 건물명이 안정적으로 추출되면 최초 업로드 시 1회 확정해 이후 재사용할 수 있으나, 기본값은 "관리사무소"로 통일해 지출처 마스터가 매달 새로 생성되는 것을 방지합니다. "3월 관리비"처럼 월 정보를 지출처명에 넣지 않습니다 — `occurred_at`이 이미 월을 표현하기 때문입니다.
- `amount`: 명세서 "납기내금액"(총액)
- `has_detail`: `false`
- 관리비 등록 여부(수동/업로드) 자체는 `TRANSACTION` 스키마를 건드리지 않고 `UTILITY_BILL_RECORD.source`로 판별합니다.
- `raw_payload`: 업로드 시 OCR 추출 원본 전체(지정+비지정 항목)를 그대로 저장합니다. 비지정 항목을 통계 화면에서 참고용으로 노출할 때 이 값을 사용합니다.

## 3. 정책

### 3-1. 총액 불일치 처리

`UTILITY_BILL_ITEM_VALUE.amount` 합계와 `TRANSACTION.amount`(고지서 총액)가 다를 수 있습니다(비지정 항목 존재 등으로). 이 경우:

- 지출 수정 화면(F-1-1-12)에서 해당 트랜잭션이 관리비 업로드 건임을 판별해 수정 시 알림을 표시합니다.
- 관리비 통계 화면에 알림 아이콘을 붙박이로 표시하고, 클릭 시 레이어 팝업으로 상세를 고지합니다.
- 사용자가 메인에서 총액을 수정해도 항목별 통계 값은 원본 그대로 유지된다는 점을 안내 문구에 포함합니다.

### 3-2. 재업로드/충돌 정책

- **케이스 A — 이미 수동 등록(`source='MANUAL'`) 존재 시 업로드 시도**: 저장을 차단하고 팝업으로 안내합니다. "이미 등록한 O월 관리비 내역이 있습니다. 관리비 내역을 삭제 후 명세서를 업로드할 수 있습니다." 시스템이 자동으로 지우지 않고 사용자가 먼저 지워야 합니다.
- **케이스 B — 이미 업로드(`source='UPLOAD'`) 존재 시 재업로드**: confirm 팝업으로 확인받습니다. "이미 등록된 O월 명세가 있습니다. 재업로드 할 경우 기존 데이터는 삭제됩니다." 확정 시 기존 `UTILITY_BILL_RECORD`(연쇄적으로 `UTILITY_BILL_ITEM_VALUE`, 연결된 `TRANSACTION`)를 삭제하고 신규로 재생성합니다.

### 3-3. 항목 선정 정책

- 최소 1개 이상 항목을 선택해야 저장 가능합니다(0개 저장 불가).
- 선정 단계는 팝업이 아닌 별도 페이지로 구성합니다(업로드 처리 완료 후 자동 전환).
- 비지정 항목은 삭제하지 않고 `TRANSACTION.raw_payload`에 원본을 보존하며, 통계 화면에서 로우레벨 리스트로 노출하고 "지정 항목으로 승격" 액션을 제공합니다.

### 3-4. null vs 0원

값이 없는 달(항목이 그 달 명세서에 없어서 패스된 경우)은 `UTILITY_BILL_ITEM_VALUE` 행 자체가 생성되지 않습니다. 통계 화면에서는 이를 실제 0원과 구분해 **"-"**로 표시합니다.

## 4. RLS / GRANT

| 테이블                    | SELECT                         | INSERT    | UPDATE    | DELETE                                                           |
| ------------------------- | ------------------------------ | --------- | --------- | ---------------------------------------------------------------- |
| `UTILITY_BILL_ITEM`       | 본인 것만                      | 본인 것만 | 본인 것만 | 없음(soft delete만) — `ITEM` 마스터와 동일 원칙                  |
| `UTILITY_BILL_RECORD`     | 본인 것만                      | 본인 것만 | 본인 것만 | 본인 것만 — 재업로드 삭제가 필요하므로 `TRANSACTION`과 동일 원칙 |
| `UTILITY_BILL_ITEM_VALUE` | 부모 RECORD가 본인 것인 경우만 | 〃        | 〃        | 〃 — `TRANSACTION_DETAIL`과 동일 원칙                            |

세 테이블 모두 `authenticated` 롤에 위 표와 정확히 같은 범위로 명시적 GRANT를 함께 작성합니다. `auto_expose_new_tables`가 기본 비활성화라 GRANT 누락 시 RLS와 무관하게 `42501 permission denied`가 발생한 이력이 있습니다(`20260701100604_grant_authenticated_table_privileges.sql` 참고).

## 5. 원본 파일(Storage) 설계

- **버킷**: private(비공개) 버킷을 사용합니다. public 버킷 금지.
- **경로**: `utility-bills/{user_id}/{period}.{ext}` — 경로 자체에 소유자 정보를 담아 RLS 정책을 단순화합니다.
- **RLS**: `storage.objects`에 대해 "경로가 본인 user_id로 시작하는 경우만" SELECT/INSERT/UPDATE/DELETE를 허용합니다.
- **열람**: 고정 공개 URL 없이, 서버가 그때그때 짧은 유효기간(TTL)의 signed URL을 발급합니다.
- **Service Role Key**: 서버/Edge Function 전용으로만 사용하고 클라이언트에 노출하지 않습니다(기존 원칙과 동일).
- **업로드 경로**: Vercel Function을 거치지 않고 클라이언트가 Storage에 직접 업로드합니다(서명된 업로드 URL 방식). Vercel Function의 요청 본문 4.5MB 제한 때문이며, 스마트폰 사진은 이를 초과할 수 있습니다.
- **압축**: 저장 전 리사이즈/압축(장당 300~500KB 권장)을 거칩니다. Supabase 무료 티어 파일 저장 한도(1GB)를 고려한 조치입니다.
- **보관 기간**: 아직 미정입니다(§7 참고). 영구 보관할지 일정 기간 후 자동 삭제할지 정책을 정해야 합니다.
- **개인정보 검토**: 관리사무소 계좌번호·연락처는 "관리단"이라는 단체 명의로 표기되어 있어, 개인정보보호법상 개인정보는 자연인에 관한 정보로 한정된다는 원칙(법인·단체 정보 제외)에 따라 원칙적으로 개인정보에 해당하지 않을 가능성이 높습니다([개인정보 포털](https://www.privacy.go.kr/front/contents/cntntsView.do?contsNo=27)). 다만 확정적 법률 판단이 필요하면 별도 법률 검토를 권장하며, 계좌번호 자체는 성격상 위 Storage 보안 조치(비공개+RLS+signed URL)로 계속 보호합니다. 동/호수 등 사용자 본인 정보는 일반 사용자 데이터와 동일 수준(RLS)으로 보호하고, 별도 마스킹(워터마크 처리)은 실효성이 낮다고 판단해 백로그로 남겨둡니다.
- **무료 티어 제약 요약** (Vercel Hobby + Supabase 무료 조합, MVP 운영 전제):
  - Supabase 파일 저장 1GB, egress 5GB
  - Vercel Hobby 함수 기본 최대 300초
  - Supabase Edge Function 무료 플랜 150초(연장 불가)
  - OCR 벤더 선정 시 이 한도 안에서 처리 가능한지가 실질적인 선택 기준이 됩니다.
